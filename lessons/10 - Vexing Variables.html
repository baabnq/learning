Lesson 10 - Vexing Variables

(Vexing means annoying, btw)

Variable Collision

If two routines use variables of the same name, that compile can not distinguish the two, because variables are global. Consider the following: 

lab routine;
    put _a = 0;
    sub subroutine;
    print _a;
    return;

lab subroutine;
    put _a = 1;
    return;
Calling routine will print 1 because the _a in routine is overwritten by the _a in subroutine. This is known as variable collision. Sometimes, collision can be resolved by just renaming one of the two variables. However, renaming might not always be possible, especially when recursion is involved.


Variable Insulation

Variable insulation is a technique for preventing variable collision. The idea is to save a variable to the stack before any overwriting would have happened. There are two types of variable insulation:

Internal Variable Insulation

In internal variable insulation the callee (routine being called) is doing the saving. 

lab routine;
    put _a = 0;
    sub subroutine;
    print _a;
    return;

lab subroutine;
    push _a; "save _a
    put _a = 1;
    pull _a; "restore _a
    return;

External Variable Insulation

In external variable insulation the caller (i'm guessing you know what a caller is) is doing the saving. 

lab routine;
    put _a = 0;
    push _a; "save _a
    sub subroutine;
    pull _a; "restore _a
    print _a;
    return;

lab subroutine;
    put _a = 1;
    return;

Internal variable insulation is obviously that preferred way of doing things, because it works for all calls of a subroutine, not just one. The only problem with internal VI is that, it is sometimes harder to implement, especially when the relevant variable is used to pull an in-parameter. Internal VI is also technically doing work that it might not have to, because the variable it's insulating might not be used by the caller.

And so, as with many things in programming: It's a trade-off. It depends on context which type of VI to use.
