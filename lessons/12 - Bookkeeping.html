Lesson 12 - Bookkeeping

Libraries in Baabnq (also called modules) are a bundled collection of routines, that act on a custom or predefined common concept. (those are concepts like Int, Chunk or Float.) If a module acts on a custom concept, this concept is usually defined by the module itself.


Module Conventions

Most modules adhere to the following layout convention, where `ModuleName` is the name of the module: 

"dependencies
use 'path/to/dep1.baabnq';
use 'path/to/dep2.baabnq';
"...

"initialize module state
sub `ModuleName`::ModuleInit;

jump `ModuleName`::Skip;
    "start of routine definitions
    
    "initializer routine definition
    lab `ModuleName`::ModuleInit;
        "initializations and concept definitions
        "...

    "other routine definitions
    lab `ModuleName`:: ... ;
        "...

lab `ModuleName`::Skip;

If the module neither has internal state nor defines concepts, only using predefined ones, then the module initializer routine may be omitted.


Structure Concept

A structure (much like in c) is a concept which divides a memory region into unique fields. Structures are not native baabnq concepts, meaning they are not directly supported by any language features. The fields of a structure are given names by declaring a variable, which stores the offset into the memory region, where that field is placed at. Consider this example definition: 

"tree structure defines Tree
"_p+0 -> content :: Int
"_p+1 -> left    :: Tree
"_p+2 -> right   :: Tree
"_p+3 -> isLeaf  :: Bool

put _`ModuleName`::Tree::CONTENT = 0;
put _`ModuleName`::Tree::RIGHT   = 1;
put _`ModuleName`::Tree::LEFT    = 2;
put _`ModuleName`::Tree::ISLEAF  = 3;

As is apparent above, structure definitions consists of two parts. The first part lays out the structure fields and offsets along with types, purely as a comment. The second part binds the offsets to the scoped field names. The layout header can follow the form `structure name` defines `type name`.

Other concept are not detailed, as they are not so common.


Nomenclature

"Allocate" / "Deallocate" always refers to a single chunk on the heap. Whereas "Create" / "Delete" refers to concepts that might consist of many chunks. These are also called "Objects", as they represent the combination of data and behaviour. Note that, "Allocate" will also zero out the chunk. For example, the behaviour of the tree structure example above might be implemented like so: 

use 'libs/stack.baabnq';

sub Tree::ModuleInit;

jump Tree::Skip;
    lab Tree::ModuleInit;
        "tree structure defines Tree
        "_p+0 -> content :: Int
        "_p+1 -> left    :: Tree
        "_p+2 -> right   :: Tree
        "_p+3 -> isLeaf  :: Bool

        put _Tree::Tree::CONTENT = 0;
        put _Tree::Tree::RIGHT   = 1;
        put _Tree::Tree::LEFT    = 2;
        put _Tree::Tree::ISLEAF  = 3;

        return;

    "=> (::Tree)
    lab Tree::Allocate;
        new 4 _pTree;

        put 0 -> _pTree + _Tree::Tree::CONTENT;
        put 0 -> _pTree + _Tree::Tree::RIGHT;
        put 0 -> _pTree + _Tree::Tree::LEFT;
        put 0 -> _pTree + _Tree::Tree::ISLEAF;

        push _pTree; sub Stack::Swap;
        return;

    "(::Tree)
    lab Tree::Deallocate;
        sub Stack::Swap; pull _pTree;
        
        free _pTree;

        return;

    "(Depth::Int) => (::Tree)
    "data Tree = Leaf | Node Tree Tree
    "createByDepth 0 = Leaf
    "createByDepth x =
    "   (\x -> Node x x) $ createByDepth (x - 1)
    lab Tree::Create;
    lab Tree::CreateByDepth;
        sub Stack::Swap;
        pull _depth;

        sub Tree::Allocate;
        sub Stack::Dup; pull _pNode;

        "write leaf property
        push 0;
        push 1;
        sub Stack::Swap ~ _depth == 0;
        pull __;
        pull __;
        put __ -> _pNode + _Tree::Tree::ISLEAF;

        "base case
        sub Stack::Swap;
        sub No::Return ~ _depth == 0;
        sub Stack::Swap;

        "create recursivly
        "construct in-frames
        push _depth - 1; "frame 1
        push _depth - 1; "frame 2

        "calls
        sub Tree::CreateByDepth; "rec call 1
        sub Stack::Swap; "swap ctx
        sub Tree::CreateByDepth; "rec call 2

        "deconstruct out-frames and recover ctx
        pull _pLeft;
        pull _pRight;
        pull _pNode;

        "link to sub trees
        put _pLeft  -> _pNode + _Tree::Tree::LEFT;
        put _pRight -> _pNode + _Tree::Tree::RIGHT;

        "done
        push _pNode;
        sub Stack::Swap;
        return;

    "(::Tree)
    lab Tree::Delete;
        sub Stack::Swap;
        pull _pTree;

        "get leaf property
        put _isLeaf <- _pTree + _Tree::Tree::ISLEAF;

        "dealloc given tree node
        push _pTree; sub Tree::Deallocate;

        "basecase
        sub No::Return ~ _isLeaf != 0;

        "get sub trees
        put _pLeft  <- _pTree + _Tree::Tree::LEFT;
        put _pRight <- _pTree + _Tree::Tree::RIGHT;

        "construct in-frame
        push _pLeft;
        push _pRight;

        sub Tree::Delete;
        sub Tree::Delete;

        return;

lab Tree::Skip;

Good practices

(See how it doesn't say "best practices")
  • When using a module as a dependency, it is generally good practice to first read the source code of the routines one intends to call.
  • Prototypes can be beneficial because developing in Baabnq is usually quite slow, so verifying integrity in higher-level language is advisable.
  • Furthermore, it is recommendable to use common sense when writing modules. (but i think you already knew that)
